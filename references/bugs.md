# Test Hub Bug 处理

通过 `sg testhub` 复用现有平台能力。本指令由 AI 编排 CLI、当前任务修复和验证，不新增另一套 Bug 状态库。

## 动作与范围

| 调用 | 行为 |
| --- | --- |
| `bug [BBS编号]` / `bug fix [BBS编号]` | 拉取该 BBS 关联 Bug，逐项复核；确认真实 Bug 后自动修复、验证、提交推送、发布测试服、回写并钉钉回复测试人员 |
| `bug list [BBS编号]` | 查看关联 Bug 的标题、状态、严重程度和负责人 |
| `bug show [BBS编号]` | 读取关联 Bug 的描述、复现步骤、评论及附件 |
| `bug create [BBS编号]` | 将当前明确的问题提交到该 BBS 关联的 Test Hub 任务 |

所有可选编号都表示 BBS ID，省略时自动读取当前阶段的 `bbs_id`。用户无需知道平台 task ID 或 Bug key；AI 按 `BBS ID -> Test Hub 任务 -> 关联 Bug` 查询后，将平台 ID 用于内部 CLI 调用和结果追踪。下文命令中的 `<testhub-task-id>`、`<key>` 均由查询结果填入，不是要向用户索取的参数。

```text
/task-workflow bug                  # 自动处理当前阶段 BBS 关联的 Bug
/task-workflow bug 57381            # 处理 BBS 57381 关联的 Bug
/task-workflow bug list 57381       # 查看该 BBS 的 Bug 列表
/task-workflow bug show 57381       # 查看该 BBS 的 Bug 详情和证据
/task-workflow bug create 57381     # 将上下文中明确的问题提交到该 BBS 关联任务
```

用户只想处理其中一项时，可描述标题或现象，例如“只修销售单保存失败那个问题”。先查询该 BBS 的关联 Bug，再按描述定位；仍有歧义时展示问题标题和现象让用户选择，不要求用户回平台查 Bug key。

自然语言“处理当前任务的 Bug”按默认修复流程执行；“看看 Bug / 分析一下”只读取证和分析。修复调用授权该范围内的代码修复、必要测试、处理评论、允许的开发状态流转、确认真实 Bug 后的提交与普通推送，以及本批已确认真实且验证通过的 Bug 所需仓库的测试服发布，不要求先开启 auto，也不再逐项询问是否推送或发布。钉钉回复测试人员按本文通知规则执行；本轮更窄限制优先，并按动作映射：只分析 / 只看 = 只读取证，不修改、不回写、不发布、不通知；不修改 = 不做代码改动，只汇报复核结果；不推送 = 可本地修改和验证，不提交、不推送；只修复不发布 = 可修复、验证、提交推送，不发布，通知只写实际进展；不要通知 = 其余动作照常，不发钉钉。未明确限制的动作按默认授权执行。PR、关闭 Bug、完成阶段不由本指令自动触发。

截图、提单 JSON 和请求 ID 等材料，有本地任务时保存在任务文档 `assets/testhub/` 下；仅持 BBS 编号查看或提单、尚无本地任务时，使用用户目录下的普通绝对目录，例如 `/Users/wuyongli/Downloads/testhub/bbs-<bbs-id>/`。这只是过程材料目录，不创建替代任务 meta 或 Bug 状态库。以下 `<key>` 子目录在查询到平台 Bug 后再使用。

## 定位当前阶段与平台任务

1. 先取用户在本次调用或明确上下文中给出的 BBS 编号。没有显式编号时，从当前任务 `meta.yaml` 自动读取：多阶段只取 `current_stage.bbs_id`，缺失时不得回退到顶层或历史阶段编号；非阶段化任务取顶层 `bbs_id`。仍无法确定时只询问 BBS 编号，不索取平台任务 ID 或 Bug key。
2. 已有本地任务时按 Load 协议读取 `meta.yaml -> index.md -> 当前 active_plan -> progress.md`，核对 BBS、绑定仓库、实际分支和已有改动。显式 BBS 与当前阶段不同，或尚无本地任务上下文时，先按 BBS 在 `_workspace/_docs` 的任务 meta 中定位正确任务或阶段；多个本地匹配时按任务名/阶段消歧。`list` / `show` / `create` 可直接对明确的 BBS 做平台查询或提单；修复必须先恢复正确的本地任务与分支，历史阶段切换仍遵循 [stages.md](stages.md)，不在当前分支修复其他阶段。修复流程未找到本地任务时说明需先绑定开发仓库；`list` / `show` / `create` 仍可按 BBS 直接执行，不因有 BBS 就自动创建工作空间。分支不一致或存在来源不明的改动时，保留现场并明确受影响范围。
3. 先核实当前 CLI：`sg testhub --help`、所需子命令的 `--help`。已有登录态直接复用；认证失败时按 `sg testhub auth login` 的设备授权流程处理，不读取或输出令牌。不要把 CLI 不可用或无权限解释为“没有 Bug”。
4. 用 `sg testhub project list --all-pages --max-items 200 --json` 获取可访问项目，有明确仓库和业务上下文时缩小到产地、批发等相关项目，不固定项目 ID。只有 BBS 编号、无法预先确定项目时，在可访问的候选项目中逐一执行下一步的精确关联查询，由结果确定项目；不能只选第一个项目，也不先要求用户补平台项目 ID。
5. 用下列命令检索候选。`--q` 是搜索线索，必须回读并核对 `bbs_number` 与本次目标 BBS 编号精确相同；字段为空的旧任务，才可用 `bbs_link` 中明确的反馈编号及业务类型核对。标题含有编号只能作为候选线索。字段与链接冲突时停止认领。

```bash
sg testhub task list --project <project-id> --q <bbs-id> --all-pages --max-items 200 --json
sg testhub task show <testhub-task-id> --json
```

搜索未命中时，去掉 `--q` 检查相关项目的任务分页，兼容仅在链接中保留编号的旧任务。多个精确匹配项时展示项目、任务 ID、名称及 BBS 关联让用户消歧；没有匹配项时报告缺少关联，不自动新建任务或修改平台关联。`--all-pages` 必须配合 `--max-items`，示例每批最多 200 项；列表有 `next_cursor` 或 `truncated` 时用返回的 `--cursor` 接续下一批，无法读完则报告查询不完整，不能断言唯一或为空。

6. 确定唯一匹配后，用平台 task ID 查 Bug，不能将 BBS 编号直接传给 `--task`：

```bash
sg testhub bug list --project <project-id> --task <testhub-task-id> --all-pages --max-items 200 --json
```

从返回列表提取每项 Bug key，后续内部 `sg testhub bug show <key>` 核对其 `project_id`、`task_id` 与上述关联一致；不一致时只报告实际归属，不修改代码或回写。用户按标题或现象限定范围时，只处理列表中匹配的项；没有限定时按默认状态规则处理全部待修项。没有待修 Bug 时输出查询结果，不制造空修复。`list` / `show` 到查看结果为止，不更新任务文档、平台状态或代码。

## 逐项复核、修复与验证

一次 `bug` 调用视为一个处理批次：批次内逐项复核、修复和验证；提交推送和测试服发布按仓库归并，平台状态流转按 Bug 逐项执行，钉钉回复按测试人员归并，不逐 Bug 单独发布或单独发送消息。本批已通过验证的项全部收敛后再进入发布；发布和回复按上述归并规则执行，验证失败、不明确或受阻项只挂起自己并如实说明，不拖住整批。

批次机器事实记录到 `assets/testhub/<bbs-id>/<batch-id>/batch.json`，至少包含每个 Bug 的 `key`、`verdict`、`repos`、`verified`、`pushed`、`published_repos`、`tester` / `tester_id`，布尔字段使用 JSON 布尔值。`verdict` 取 `real` / `unclear` / `not_bug` / `blocked`；`repos` 和 `published_repos` 使用绑定仓库 key，后者是前者子集；`published_repos` 记录该 Bug 所需仓库中已在测试服生效的仓库，无历史成功记录时初始为空。接续时只保留对应当前待验证修复版本、仍有效的已发布仓库；若本轮或后续为该 Bug 的某仓库推送了新提交或产生了新修复版本，必须先将该仓库从 `published_repos` 移除并重新发布，不能沿用旧发布证据。本批次新发布成功的仓库再补入。`verified` / `pushed` 表示该 Bug 所需全部仓库的汇总状态，只有全部仓库完成才记为 true，`verdict=real` 时必须显式给出 JSON 布尔值；`note` 可选，记录挂起原因。`tester` 是平台任务回读的复测人完整姓名，单个 Bug 有更明确的复测人时以该 Bug 为准；`tester_id` 仅是 Test Hub 平台关联 ID，不参与钉钉收件判断。同一人个别项缺 `tester_id` 时脚本按同批姓名补全，同名对应多个 ID 会保留 warning 而不强行合并。

```json
{
  "batch": "2026-11-12-1",
  "bugs": [
    {
      "key": "BUG-123",
      "verdict": "real",
      "repos": ["producer-backend"],
      "verified": true,
      "pushed": true,
      "published_repos": [],
      "tester": "张三",
      "tester_id": "u1"
    }
  ]
}
```

用 `python3 /Users/wuyongli/Documents/sg-skill/task-workflow/scripts/plan_bug_batch.py --input <绝对路径>` 归并待发布仓库、可转待验证项和按测试人员分组的回复计划，再按计划执行；脚本只做计划与一致性校验，不复核结论，也不执行发布、状态流转或发送。`published_repos` 不在 `repos` 中会作为计划错误停止，必须先修正仓库 key。`notify` 按 `tester` 完整姓名分组；`waiting_publish` 表示待发布或发布未成功，通知时按阻塞或进展说明，不写成可复测；`unassigned` 表示缺少可核实的测试人员姓名，保留待通知并说明原因；`tester_id` 只作平台关联，不作为发送门禁，`tester` 非空但同名对应多个 `tester_id` 时保留 warning，发送前按姓名澄清实际收件人。`publish_repos` 为空时跳过发布；发布必须显式传入计划中的仓库 key，不无目标调用发布脚本。以脚本逐仓 `[OK]` / `[FAIL]`（预检）/ `[FAILED]`（执行失败）/ `[UNCERTAIN]` / `[CONFLICT]` / `[RESTORE_FAILED]` 结果为准；`[RESTORE_FAILED]` 表示发布已成功但切回任务分支失败，按发布成功记录测试服证据并计入 `published_repos`，同时报告分支恢复失败待人工处理。发布完成后按实际成功仓库更新 `published_repos` 并重新运行脚本，只把输出为 `pending_verify` 且平台回读成功的项转待验证。

- 默认修复 `new`、`assigned`、`in_progress` 的关联 Bug；`closed` 跳过，`pending_verify` 列为待测试人员验证，避免重复处理。用户明确要求复查指定项时可重新取证；发现待验证版本仍有缺陷时继续修复，状态操作仍按下节规则。已关闭项需要重新打开时说明证据，不擅自重开。
- 复核后先给出结论：有复现或代码、日志证据且预期行为明确的，判定为真实 Bug 并进入自动修复；无法复现、证据不足、符合已确认行为或业务口径未定的，不修改代码，记录复核依据和待补信息，并按通知规则如实回复，不为了推进而盲改。
- 逐项独立推进：不明确、待讨论或受阻的项只挂起该项，不阻塞本轮其它已确认真实 Bug 的修复、验证、推送、发布和回复；同一 Bug 内明确部分照常修复，未决部分单独列出。同一 Bug 涉及多个仓库时，只有全部所需仓库验证通过并推送后才进入发布交测；部分仓库未完成时保留已修复现场，不发布半成品，也不把这个 Bug 的其他仓库算作已交测。
- 接续仍在 `in_progress` 的 Bug 时，先核对已有修复、验证、推送及测试服发布证据。修复已验证并已推送但仍待发布时，复用现有记录并继续处理其他项；已通过验证但尚未推送的按本轮授权补齐提交推送。若本轮为该 Bug 的某仓库推送了新提交或产生新修复版本，必须先把该仓库从 `published_repos` 移除并重新发布，不能沿用旧发布证据交测。测试服已包含当前完整修复且仅缺状态流转时，直接补齐待验证流转，复用已经回写的评论。
- 每项先读取详情及完整上下文：

```bash
sg testhub bug show <key> --json
sg testhub bug context <key> --all-pages --max-items 200 --json
```

- 查看复现步骤、实际与预期结果、环境、关联任务、评论、截图与其他附件。按上下文的附件、评论、采集记录各自游标，用 `--attachment-cursor`、`--comment-cursor`、`--capture-cursor` 补齐对应分页；需要图片时用 `context --images-dir <绝对目录>`，按 `images.next_image_offset` / `remaining_ids` 配合 `--image-offset` 继续下载，并实际查看下载图片。文件放本次材料目录的 `<key>/` 下，目录使用用户目录下的普通绝对路径，避免 macOS `/tmp` 符号链接路径。未能读取的附件明确标为证据缺口，不声称已检查。
- 按严重程度、依赖和影响范围安排顺序；共享根因可合并修复，但每个 key 保留单独的复现、验证和回写结果。一项受阻或不明确时继续不依赖它的项，不因个别未决项暂停整批处理，不扩展到未绑定仓库或其他阶段。
- 先复现或取得代码、日志等足以定位的证据，在当前 plan 收口预期行为、最小修复与验收条件；明确技术 Bug 直接诊断，业务口径不明确才按需使用 `product-copilot-rules`。修复调用提供范围内开工授权：明确技术 Bug 的最小方案由 AI 基于证据写入 plan，不再逐项索要开工确认；关键业务事实不明则暂停该项并补问。满足开发准入后同步 `status`、`current_stage.status`（有则同步）及 `coding_allowed` 再修改。暂停任务仍须明确恢复，不因检测到 Bug 自动解除暂停。
- 沿用当前任务记录分支和绑定仓库，不为每个 Bug 自动新建任务或 `next`。保留无关本地改动，按项目模式最小修复，有长期回归价值时补测试。
- 按 [verification.md](verification.md) 验证原始复现路径和受影响的关键回归，页面、接口、数据库证据按缺陷实际涉及的层面选择；按 [runtime.md](runtime.md) 使用当前任务环境，后端测试在当前任务专属 Docker app 中执行。不能只凭单测通过就声称原始页面问题已修复。
- 验证失败则在当前范围修复并重测；同一问题连续修复验证最多 3 轮，仍失败或关键环境/数据缺失时记录具体阻塞、未覆盖项及解除条件，不降低验收标准。
- 批次内已通过必要验证的真实 Bug 全部收敛后，按仓库归并提交并普通推送本批修复，同一仓库不因多个 Bug 重复推送；同一仓库可合并为一个或多个提交，但 `progress.md` 必须记录每个 Bug 对应的提交。验证失败或受阻项保留本地现场，不进入本批提交推送和发布。无需逐项询问推送；按 [Save / Push](publish-sync.md#save--push) 核对提交、远程 SHA 与 ahead / behind。只提交本批 Bug 修复及必要测试，不混入无关 dirty 文件，不创建空提交，不 force-push 或跳过 hook；无法安全区分原有改动时说明阻塞，不打包全部改动。
- 本批已通过验证的项全部处理完并推送后，对受影响仓库统一执行测试服发布，同一仓库只发布一次，不逐 Bug 重复发布。发布前先按相同候选仓库 key 集合调用 `clean_develop_task_workspace.py <task-id> <仓库 key...>`；再把 clean 结果为已删除或 no-op 的仓库 key 传给 `publish_task_workspace.py <task-id> <仓库 key...>`，clean 普通失败的目标不得发布，develop 冲突或重试现场按 [publish-sync.md#publish](publish-sync.md#publish) 的例外保留并继续。沿用该参考的 develop 冲突处理、成功信号判定和失败边界，不手工拼接发布命令；本轮明确“只修复不发布”时保留待发布记录。发布范围只覆盖本批已确认并验证通过的 Bug 所需仓库，不等待不明确或受阻项；发布失败或结果 `UNCERTAIN` 的仓库不阻断其它已成功仓库的 Bug 交测。

## 回写处理结果与状态

每项在 `progress.md` 记录 key、平台项目/任务 ID、根因、涉及仓库、修复及验证证据、阻塞和下一步；`index.md` 保留摘要，稳定方案归并当前 plan。平台关联每次执行仍需回读核对，不以本地历史记录替代。

本批已通过必要验证的项，按仓库统一提交并普通推送到当前任务分支，核对远程结果；本批这些项全部处理完后按上节统一发布测试服。发布成功后按批次回读确认测试服包含各 Bug 所需全部修复，再逐项转 `pending_verify`，最后按测试人员合并钉钉回复。发布失败、结果不确定或尚有依赖仓库未成功发布时，在 `progress.md` 标记“已修复并推送，待发布测试服”或“发布结果不确定”，按 Bug 记录所需仓库、修复提交、远程核验和发布证据；依赖未满足的 Bug 保留实际状态，不提前转待验证；验证失败、不明确或受阻项单独保留现场，不进入发布交测。已发布部分保留对应发布记录，供分批发布时继续核对。本轮因发布失败或明确限制未发布的项，以及后续追加的 Bug、优化，下次执行 `bug` 时按 [publish-sync.md](publish-sync.md#普通发布与-bug-交测的边界) 接续；普通 `publish` 不自动交测或通知。

1. 回写前重新 `bug show`，核对归属、当前状态、`version`、`capabilities.can_comment` 和 `capabilities.allowed_transitions`。允许的目标及必填字段以返回值为准，同时检查 `conditional_required_fields`，不写死角色权限或补造负责人、修复版本等信息。
2. 修复调用包含处理结果评论授权。评论说明根因、修复范围、真实验证结果、代码是否提交/推送、部署情况及待验证步骤；受阻时说明已完成部分和阻塞。使用 `--input <绝对JSON文件路径>` 传入 `{"body": "处理结果正文"}`，保存在本次材料目录的 `<key>/` 中，避免多行文本的 shell 转义问题。
3. 每次评论操作生成并记录独立的 `--request-id`，同一操作恢复或重试时复用，内容改变则使用新 ID。超时或结果不明先重新读取上下文核对；确认已成功不重复追加评论。无法核实则报告“回写结果不确定”，不盲目重放。
4. 开始修复时，仅在平台允许且所需字段已确定时进入 `in_progress`。保留现有负责人，按平台允许的路径流转。
5. **测试服包含完整修复后转待验证。** 复核确认缺陷存在、修复完成、必要验证通过，并确认测试服已成功发布该 Bug 所需的全部修复后，在平台权限允许的范围内执行 `transition ... pending_verify`，附上实际测试服版本和复测说明。仅完成提交、推送、PR、评论，或仅部分仓库的修复已发布时，保留实际状态并记录剩余发布项。

状态迁移与评论分别核对。即使评论已成功，仍须完成待验证迁移；评论权限不足或提交失败时单独报告，已具备交测证据且允许迁移的 Bug 仍可在迁移备注中附上验证说明。迁移前重新 `bug show` 获取最新 `version`。按目标的 `required_fields` 和 `conditional_required_fields` 填参数，目标允许填写解决结果时使用 `fixed`，需要 `fix_version` 时填写实际交测版本。

```bash
sg testhub bug transition <key> pending_verify --version <fresh-version> --note '<修复摘要、交测版本和复测步骤>' --json
```

根据返回的迁移要求和当前 `--help` 补齐参数，例如 `--resolution fixed` 或 `--fix-version <实际版本>`。平台只允许先进入 `in_progress` 时，按允许的迁移路径执行并回读，再以新版本号提交待验证。版本冲突时重新读取状态、权限和他人的更新，重新判断原动作是否仍适用。普通网络失败先核对结果，最多再尝试 1 次。非幂等状态操作结果不明且无法核实时停止。

6. 以 `bug show` 回读到 `status: pending_verify` 作为交测流转成功证据。已是待验证时跳过重复迁移。若回读仍为 `in_progress`，逐项报告实际状态和原因，例如权限不足、缺少实际交测版本或迁移失败，记录为流转未完成。用 `bug context` 核实评论结果，分别写入本地进度。测试人员最终验收、关闭 Bug 和任务阶段完成各按其独立授权处理。

### 钉钉回复测试人员

- 本轮测试服发布成功并回读确认相关 Bug 已为 `pending_verify` 后，按已授权的交测通知，通过 DWS 钉钉单聊回复测试人员；本轮“只分析 / 不要通知”等限制优先。发布失败、结果不确定、仅部分仓库成功或平台流转失败时，按实际状态回复已完成修复、推送和发布情况、阻塞及可复测范围，不把未发布或未流转成功的项写成已可验证。
- 无法复现或判定非缺陷的项也按复核结论回复，不写成已修复；此类项不进入发布交测，也不因存在未决项而延后其它已确认项的通知。可与可复测项合并在同一条消息中分段说明，但必须逐项标明状态。接续时可补发该交测轮次已记录为未发送的通知，先核对状态与测试服版本仍适用。
- 用 `sg testhub task show <testhub-task-id> --json` 回读 Bug 关联任务的 `tester`（完整姓名），用户明确指定复测人时以本轮指令为准。拿到姓名后按 [钉钉收件人核对](dingtalk-recipient.md) 统一核对收件 ID；`tester_id` 是 Test Hub 平台内关联 ID，不能直接当钉钉收件 ID。缺少测试人员、身份无法唯一核实或需要跨组织发送时，保留待通知并说明原因。
- 按批次计划脚本输出的 `notify` 分组发送，同一批次同一测试人员合并一条消息，列出本批全部可复测 Bug 和未决项，不逐 Bug 单独发送；`tester` 为空的分组不发送，先补核测试人员；`tester_id` 不代表钉钉收件 ID，发送门禁按姓名核对结果而不是 `tester_id` 是否存在；同名对应多个 `tester_id` 时先按姓名澄清实际收件人。写明任务及阶段、BBS 编号、待验证或已处理 Bug 的编号与标题、已核实的测试服版本及复测要点；发布失败或不确定时写明阻塞项和可复测范围。有已核实的 Bug 链接时附上链接。
- 发送前在 `progress.md` 保存本次通知的收件人、处理轮次及 Bug 范围、发送 UUID。确认发送后登记结果和可用回执。已成功发送且结论、测试服版本、可复测范围均未变化的轮次跳过重复通知；此前只发过失败、待发布或阻塞说明，本次结论变化的，生成新版补发。发送超时先核对单聊结果，确需在 DWS 去重期限内重试时复用同一 UUID。结果仍不明则标记“通知结果不确定”，等待核实。通知失败单独汇报，保留已确认的 Test Hub 状态。

按 DWS 当前命令帮助发送；标题按通知类型填写，例如可复测通知用 `测试服 Bug 待验证`、发布异常说明用 `Bug 处理进展`。收件人始终是上文核对的测试人员，与 `fix` 的 PR 审查人无关；收件 ID 与 `--user` / `--open-dingtalk-id` 的选择按 [钉钉收件人核对](dingtalk-recipient.md)。已核对的单聊形式如下。

```bash
dws chat message send --user '<已核对的 userId>' \
  --title '<测试服 Bug 待验证 / Bug 处理进展>' --text '<交测说明或处理结果>' --uuid '<已记录的通知 UUID>' --format json
```

## 提交新 Bug

`bug create` 表示授权创建该问题。先按上述规则定位平台任务，检索相同任务下的已有 Bug，核对复现与环境避免重复；已有同一问题时返回其 key，未获补充评论授权时不自动发评论。

根据当前 `sg testhub bug create --help` 整理项目、平台 task ID、标题、复现步骤、实际结果、预期结果、环境和严重程度等必需信息。已观察到的事实直接填入，未复现不写成“已复现”；缺少影响提单的必要信息时只补问缺项。描述中带当前 BBS 关联与受影响端，不把口令或个人敏感数据放入附件。

通过 `sg testhub bug create --input <绝对JSON文件路径> --request-id <已记录的操作ID> --json` 提交。JSON 使用接口字段 `project_id`、`task_id`、`title`、`severity`、`reproduce_steps`、`actual_result`、`expected_result`、`environment_type`、`environment_detail` 等；不要将 CLI 的 `--project` / `--task` 直接写成 JSON 的 `project` / `task`。枚举值以当前 CLI/客户端声明为准，不从中文标签猜值。创建后 `bug show` 回读项目、任务归属及关键内容，记录返回 key。结果不明按评论相同的幂等与有限重试规则处理，不重复建单；附件上传仅在用户要求或提单所需证据的授权范围内执行。

## 输出

以 BBS 编号和任务名说明处理范围，逐项按问题标题说明复核结论、根因或阻塞、修复与验证结果、提交推送与远程核验、平台回写后的真实状态及钉钉回复结果；平台 Bug key 可作辅助追踪，不作为用户后续调用的必填信息。代码提交推送、发布和业务验收分别陈述；只读查询、无待修项或部分失败时直接说明事实。
