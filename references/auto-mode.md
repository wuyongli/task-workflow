# 自动开发模式

适用于用户明确要求开启或继续自动开发的当前任务空间。常规模式保持原有协作行为。

## 启用与恢复

唯一新增机器字段为顶层 `meta.yaml.execution_mode: manual | auto`，缺省为 `manual`；非法值应报告并停止该任务，不能猜测。全任务状态列表对异常任务单独报错后继续展示其他任务，并返回非零退出码。模式属于任务空间，不写入 `current_stage` 或 `previous_phases`，也不从阶段字段推断模式；`next`、`stage` 和换会话均保持同一个开关。独立创建的其他任务空间仍缺省 manual。

```bash
python3 /Users/wuyongli/Documents/sg-skill/task-workflow/scripts/set_task_execution_mode.py "YYYY-MM-DD-任务名" auto
python3 /Users/wuyongli/Documents/sg-skill/task-workflow/scripts/set_task_execution_mode.py "YYYY-MM-DD-任务名" manual
```

脚本支持 `--dry-run`，只设置任务空间模式，不改状态、编码许可、业务文件或 Git，不判断产品准入。AI 执行脚本后同步以下内容再推进：

- 当前 plan 的“开发准入确认”：记录用户启用指令、当前阶段范围、验收要求和特殊限制。复用已有明确授权，不机械再次确认；不能把仅有的字段值当作未记录范围的无限授权。
- `index.md`：在任务摘要展示执行模式，保持与 meta 一致。
- `progress.md`：紧凑记录模式切换和下一步，不新建授权、目标或执行状态文件。

启用自动模式默认授权在当前明确范围内确定方案、开发、必要的本地依赖准备、本地缺失数据库结构补齐（边界见下）、自测、审查修复、提交和推送任务分支。若用户说“只切换模式，暂不执行”，则本轮只设置模式。`next` 新阶段和 auto 任务的 `stage` 切换均先令 `coding_allowed: false`；AI 核对目标阶段自己的 plan、范围、验收和既有指令后才能恢复编码。新阶段沿用自动模式，但不能拿旧阶段方案替代新阶段准入；已有授权覆盖时不重复询问。

暂停和常规模式不同：`manual` 只关闭自主连续推进；用户要求暂停任务时按现有 `status: 暂停中`、`resume_status` 保存现场，并将 `coding_allowed` 置为 false。暂停任务不能因仍是 `auto` 就自动恢复，须有明确继续指令；修改模式本身也不恢复暂停任务。

## 指令优先与开发准入

- 当前明确的“只分析”“只审查”“只保存”“不改代码”限制优先，不因为 auto 扩大本轮动作；单独 `load` / 状态查询仍只读。本轮临时限制不自动永久改写模式。
- 读 `meta.yaml -> index.md -> 当前 plan -> progress.md`，核对绑定仓库、实际分支、已有改动和提交；未知来源的 dirty 文件保留现场，不覆盖也不擅自纳入提交。当前任务或阶段存在 `bbs_id` 时，先执行 `sg bbs demand view <bbs_id> --with-ai --json` 读取 BBS 正文和 `aiAnalysis.rawText`，把 AI 分析作为需求线索与取证入口。
- BBS AI 分析不是用户确认、代码事实或数据库验收证据；必须回到当前仓库代码、配置、任务文档和必要的本地 / 测试环境核验。AI 分析中的历史数据结论、风险判断和推荐方案只能记录为“外部分析 / 待核验”，不能直接据此修改数据、扩大范围或跳过开发准入。
- 任务目标、范围和验收足够明确时，AI 可取证并自行确定范围内方案，记录“AI 依据用户预授权确定”，不能写成“用户已确认”。明确技术 Bug 直接走诊断和最小修复，不强制完整产品流程。
- 当前 plan 中方案和开发落点可执行、没有影响开工的关键待确认项、授权覆盖当前动作且本轮没有更窄限制时，才进入 `开发中` 并更新 `coding_allowed: true`。模式不替代准入判断。
- 核心业务事实缺失、口径有歧义或必须扩大范围时，完成可做的分析并提出推荐意见，保存阻塞和最小待确认事项；不得靠编造业务事实继续实现，也不得自行改写授权范围。
- 新缺口使当前阶段整体不再满足准入时，将顶层和当前阶段状态同步为 `暂停中`，用 `resume_status` 保存原状态并令 `coding_allowed: false`，保留 auto；收到澄清及继续指令后重新判断准入。仅局部依赖受阻时在 plan/progress 明确受阻范围，独立且仍满足授权的部分可继续，不将整个阶段误报为已交付。

## 自动闭环

1. 分析与方案：在当前 plan 收口目标、系统证据、实现和验收，并按 [verification.md](verification.md) 的“自动模式真实流程测试”明确本任务适用的页面、接口、数据库断言与测试数据；不额外等待范围内技术决策确认。
2. 开发与代码检查：按改动点实现，使用任务 runtime 运行必要单测、类型检查等；有长期回归价值的行为改动补测试。后端报错可读取当前任务 Docker 日志，日志取证不受模式限制。
3. 真实流程自动测试：页面、真实接口和数据库结果核验属于自动开发职责，不默认转交用户。涉及页面操作的缺陷按原始操作路径自动操作真实页面；涉及后端请求、持久化或计算结果的任务验证真实接口及对应数据。仅 mock 单测通过不能替代这些验证。具体环境、证据、适用性与阻塞处理按 [verification.md](verification.md) 执行。
4. 审查修复：按 [review.md](review.md) 完成默认完整审查；发现当前范围内缺陷，自动修复并重跑受影响的代码检查与真实流程测试。同一问题最多连续修复验证 3 轮，仍失败则记录阻塞，不进行无关重构。
5. 提交推送：本任务必需的代码检查和真实流程自动测试通过、无未解决阻塞缺陷后，按绑定仓库提交和普通推送；排除无关文件、不 force-push、不跳过 hook。无改动仓库不创建空提交。必要测试受阻时可按既有授权保存已完成代码，但必须标为“已保存、自动验证受阻”，不得因此宣称闭环完成。
6. 收口：核验远程任务分支 SHA、工作区和 ahead/behind，记录实际测试证据。自动测试全部完成后仍保留 `测试中` 等待用户最终业务验收，不自动 complete、cleanup、PR、合并或发布；这里的用户验收不代替 AI 应执行的自动测试。已推送但真实流程未验证的任务，恢复时从未完成的测试继续，不能按已交付任务跳过。

内循环审查修复和提交已包含在启用授权中，不按独立 review 的只读默认或单独 save-only 的停止边界截断整个自动开发流程。用户本轮单独调用 review / save-only 时仍遵守它们原有边界。

## 等待人工时释放任务资源

- 任务进入待人工测试、自动测试完成等待业务确认、或阻塞/暂停后必须由用户介入时，先保存进度，再停止该任务专属 Docker app 实例，避免占用后续任务资源。仅进入 `测试中` 但 AI 仍在主动自测时不停止正在使用的实例。
- 停止前核对 meta 绑定仓库、compose project、容器及实际挂载路径。复用既有 runtime stop 实现或任务 compose 的 `stop app`；不用 `docker pause` 挂起保留内存，不执行全局 stop/down，不停止共享 MySQL/Redis/Mongo/RabbitMQ，不删除容器、volume 或任务数据，也不影响其他任务。
- 本次启动且不再需要的任务前端进程一并停止；不得结束未知来源或其他任务进程。用户明确要求保留环境供现场验收时遵从用户指令。
- 核验容器已停止并在 progress 和钉钉里程碑记录释放结果；失败则报告残留实例，不声称已释放。恢复时按用户继续指令及任务准入，用仓库既有启动动作重新启动，核对就绪、代理和数据环境后继续。

## 钉钉进度推送

- 自动开发过程的里程碑进度推送到钉钉群“国庆任务进度推送”。发送前用 `dws chat search --query "国庆任务进度推送" --format json` 按群名解析当前 `openConversationId`，不把历史群 ID 固定写入任务文档或代码。
- 每条消息必须以任务名称开头或放在标题中，BBS 编号只能作为辅助标识。至少包含：任务名称、BBS 编号（有则写）、当前阶段、当前状态、刚完成的动作、验证结果或阻塞、下一步。
- 在以下节点推送一次：开始接续任务、阶段切换、方案准入完成、开发完成、自测完成、审查修复完成、提交 / 推送完成、出现阻塞、任务收口。连续的命令、同一阶段内的普通取证和重复重试不逐条推送。
- 任务名称以当前任务空间 `meta.yaml.current_task_name` / `current_stage.task_name` 为准；BBS 标题只作为交叉核对信息，不能替代任务空间名称。多阶段任务必须同时写明阶段名称，避免只报 BBS 编号无法分辨。
- 推送内容只陈述已发生的事实，不把“开始处理”写成“已完成”，不把本地测试写成真实页面、测试服或客户验收；失败和未执行项必须明确说明。
- 群消息发送失败不阻断代码开发、测试或提交，但要在 `progress.md` 记录推送失败和下一次补发节点；不得因通知失败伪造进度。

## 失败与恢复

- 测试失败：修代码或环境原因并补测，不删断言、降验收标准或把失败说成通过；必要验证因账号、数据或环境缺失无法执行时暂停交付，保留已验证事实。
- hook 改写文件：检查差异，属于当前任务的格式修复可保留，补跑失效的相关验证后重新提交；hook 失败可在授权范围内诊断修复，最多重试 2 次，不使用 `--no-verify`。
- 网络失败：最多重试 2 次，每次先核对远端实际结果。推送结果不明时先查远程 SHA，已成功则不重复提交；持续失败保留本地提交和阻塞记录。
- 多仓部分成功：逐仓保存结果，任务不算完整交付；恢复时只处理未完成仓库，已推送的结果需与实际 Git 状态核对。
- 主线同步冲突仍按 sync 的停止规则处理，不因 auto 自动改写历史。共享基础设施变更和外部通知等不属于默认自动开发授权，遵守用户既有授权和相应规则。
- 恢复时根据 progress 和实际代码决定从哪一步继续；按 [verification.md](verification.md) 区分历史证据与本轮验证，不把历史测试当成本轮新执行。已交付且没有新要求、代码或环境变化时，只汇报已有交付和待人工验收项，不反复启动开发、审查或创建提交。

## 数据库范围

- 自动模式只允许访问已确认的本地数据库和测试服数据库，不得连接、查询或修改生产数据库；环境无法确认时停止数据库操作，不能按库名或默认配置猜测环境。
- 先读取当前仓库的配置与数据库初始化代码，确认实际连接环境、业务库和目标表；只读检查与隔离测试库的正常自测属于自动开发范围。
- 本地数据库：允许只读取证；隔离测试库中，既有测试流程需要的测试数据准备与清理属于自测。启用自动模式的授权包含：为当前任务开发、自测或联调，按当前后端生效模型最小补齐本地库缺失的表、字段、索引（包括主线已合入的定义），无须逐次再次确认。使用 `local-db-repair` 时，这属于已有的本地 DDL 明确预授权；本轮“只分析 / 不改数据库”等更窄指令仍优先。
- 本地补齐前必须核对实际连接确为本地库、当前代码模型与真实 schema，明确字段类型、默认值、可空性和索引约束，不从报错猜定义；新表优先使用项目已确认的模型注册和初始化入口。执行前简述缺项和最小修复，执行后回读 schema 并重跑触发问题的请求或测试。临时 SQL 不进入业务仓库，实际补齐和验证简记到任务记录。
- 本地结构预授权不包含删除、重命名、改字段类型、清库、批量回填业务数据或其他数据修复；补齐涉及已有数据冲突、定义不明确或必须做这些动作时停止相应操作。
- 测试服数据库：默认只允许 `SHOW`、`DESCRIBE`、`EXPLAIN`、`SELECT` 等只读验证；数据写入和 DDL 必须有用户针对该动作的明确授权。“允许访问测试服”不等于允许改测试服数据。
- 查询遵守当前项目的数据库访问规则，先确认库表和结构，再执行窄条件、小样本查询；SQL 使用明确的库名限定表名。不为自测切换共享数据库数据目录，也不把远程数据库变更包含在普通代码推送中。

自动模式没有定时唤醒、会话编排或多任务锁功能；这些由后续调度层负责。调度层必须遵守 [dispatch.md](dispatch.md)，统一以任务名称和阶段推送里程碑，不能只推送 BBS ID。
