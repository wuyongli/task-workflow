# 发布、同步与推送

## 目标识别

`publish` / `sync` / `clean-develop` / `pr` / `save-push` 共用目标识别规则：
- 默认从当前任务上下文识别当前要操作的任务，不额外要求用户重复提供 task 标识
- 如果当前上下文无法唯一识别任务，才向用户补充确认
- 目标表达的核心是“目标分类”，不是固定仓库名；执行时需要在当前任务绑定仓库里动态匹配对应的后端、手机前端、PC 前端仓库
- 常见说法包括 `后端`、`手机前端`、`PC前端`、`前端`
- 如果用户只说“前端”，且当前任务里只有一个前端仓库，可以直接匹配；如果同时存在手机前端和 PC 前端，则应要求用户明确
- 多目标 PR 默认并行，单个仓库失败不阻断其它仓库；发布、同步和清理的并行及失败处理见各自章节

## 验证去重

- PR 和发布前按 [verification.md](verification.md) 执行当前消息所需验证；如果同一轮响应内已经完成最终验证且相关 tree 未变化，不得仅因提交、推送或创建 PR 重跑
- 用户只要求保存、提交或推送代码到远程时，按 save-only 处理；不因为保存代码主动运行 test、typecheck、lint、build、完整 runtime prepare 或前端依赖修复
- 跨消息记录只用于说明对应 SHA 的历史结果和选择本轮验证范围，不能替代当前消息要求的新鲜验证
- 发布后的真实页面、接口或测试服数据属于环境验收，按需重新验证，不能只用本地测试代替
- 如果用户或项目上线闸门明确要求重新执行，以明确要求为准

## PR

显式命令：

```text
/task-workflow pr [目标1] [目标2] [...] [--title <标题>] [--desc <描述>] [--reviewer <用户>]... [--task-link <BBS链接>] [--no-wip]
```

规则：
- 用户显式输入 `/task-workflow pr ...`，或明确要求为指定任务仓库创建合并请求时，即授权对选中仓库的本任务改动执行必要验证、提交、普通推送，再创建或复用 PR；不因尚未提交重复询问 commit 授权。查看、列出或评审 PR 仍是只读动作，不据此提交推送或创建。
- 本轮“不要提交 / 不要推送 / 只准备说明”等更窄限制优先；限制使创建前置条件不成立时说明缺项，不绕过限制。自动提交仅保存已授权的本任务成果，不新增业务实现、自动修复审查问题、发布、合并或标记任务完成。
- 默认不指定目标时，处理当前任务下全部绑定仓库；指定目标时，继续使用和 publish / sync 一样的自然语言目标识别方式
- 一次多个目标时，先统一识别并校验候选目标，再基于实际改动过滤出要创建 PR 的仓库；一个仓库失败不阻断其它仓库
- 候选目标来自当前任务绑定仓库；不要脱离 `meta.yaml` 绑定仓库去全局找仓库，也不要要求用户重复说明仓库路径或分支
- 源分支直接使用 `meta.yaml` 中该仓库记录的任务分支；目标分支默认使用仓库远程默认分支，用户明确提供目标分支时才覆盖
- 创建前先加载当前任务的 `meta.yaml`，确认目标仓库存在、当前分支与记录分支一致，检查 `git status --short --untracked-files=all`、已暂存 / 未暂存 diff 及任务相关未跟踪文件。明确属于本任务的未提交改动进入下方自动提交步骤，不以“工作区尚未干净”阻断；分支不一致、未解决冲突或改动归属无法判断时停止对应仓库，不切分支、reset 或解冲突。
- 完成基础校验后，对当前阶段全部绑定仓库 `fetch origin --prune`，只读检查记录任务分支相对 `origin/<远程默认分支>` 的三点 diff，并结合本任务的已暂存、未暂存及未跟踪改动，得到配套改动集合。不能只看已提交 diff，就把仅有工作区改动的仓库跳过。未选中的仓库仅用于判断配套端，不切换分支、不提交推送、不创建或修改其 PR；其工作区与记录分支不一致时，不把该工作区内容算作任务改动。
- 创建前先解析全局 `sg` CLI：运行 `which -a sg`、`sg --version` 和 `sg pr create --help`；如果存在多个 `sg`，优先使用版本更高的可执行文件绝对路径
- 参数以实际执行的新版 `sg pr create --help` 为准，例如使用 `--task-link`，不得凭记忆写成 `--task_link`
- `sg` 是全局工具，不按仓库分别判断版本；但 `sg pr status`、`sg pr create`、`sg pr view` 等命令必须在目标仓库根目录执行
- 如果实际执行到 `/usr/local/bin/sg 0.0.2-alpha.8` 这类旧版，或 help 缺少 `--task-link`、`--reviewer`、`--wip` 等当前流程需要的参数，先修正全局 `sg` 入口或使用新版绝对路径，不要继续创建缺少 BBS 关联或 WIP 标记的 PR
- 先运行 `sg pr status` 检查当前分支并记录已有开放 PR。存在开放 PR 时仍先完成本轮相关改动的验证、提交和推送，再复用并输出该 PR 的状态和链接；不要因查到 PR 就提前结束，也不重复创建。已有开放 PR 仅在本次明确继续准备上线或重新操作 PR 时，允许按下方规则最小更新标题日期，不自动关闭、合并或重试远程 PR 操作。
- 对选中仓库，按 [verification.md](verification.md) 完成受影响的最小充分验证，可复用同轮仍有效的最终验证。验证失败或受阻时报告实际证据，停止该仓库的自动提交 / 推送及 PR 创建，不把创建 WIP 当作绕过验证的理由；用户另行明确只保存时才按 save-only 处理。
- 验证通过后，按本任务相关文件或可安全分离的片段暂存并检查 `git diff --cached`，每仓独立创建中文描述的提交。核对原有暂存内容，排除无关改动、凭证、本地运行配置和临时产物，不直接 `git add -A` 打包；无法安全分离时只说明具体阻塞，不能提交无关内容。无可提交改动不创建空提交，已有未推送提交仍进入推送步骤。
- commit hook 失败时展示输出并停止该仓库；hook 改写文件或暂存区时先展示变化并停止自动接续，不能沿用已失效验证继续创建 PR，也不自动重试提交、跳过 hook 或修复无关环境。正常提交后核对提交 tree 与本轮验证内容一致；不一致时按验证规则重新判断所需检查。
- 将选中仓库的任务分支普通推送到 `origin`：远程任务分支尚不存在或尚未建立自己的 upstream 时执行 `git push -u origin <记录分支>`，否则普通推送到该任务分支；不把内容推到远程主分支，不 force-push、amend、改写历史或自动拉取 / 合并。本地落后于远程、分叉或 push 失败时停止该仓库后续 PR 写操作，保留现场。
- 提交推送后核对远程 SHA、ahead / behind 和工作区状态，分别报告本任务成果是否保存及无关 dirty 文件是否仍保留。已成功提交的仓库按最终提交重新计算三点 diff；其它配套仓库（含未选中、验证失败或提交失败的仓库）仍结合其已核实的工作区任务改动，更新配套端集合。失败仅阻断该仓库的 PR 写操作，不使其实际改动从其它 PR 的配套端标签中消失。通过前置步骤但没有本次 PR diff 的选中仓库跳过新建，并列为“无本次 PR 改动”，不为此关闭已有 PR；失败仓库仍按实际失败原因报告，不误报无改动。
- 未指定 `--title` 时，默认标题仅为 `任务名（有其他配套端）`；新版 `sg pr create` 会自动添加当天日期和从 `--task-link` 解析的 BBS 编号，task-workflow 不得将任务日期或 `bbs_id` 再传入 `--title`
- PR 标题里的日期按本次 PR 操作日 / 预期上线日理解，不按任务创建日理解；如果用户明确给了上线日期，优先使用用户指定日期
- 如果用户指定的上线日期不是当天，新建 PR 后也要先用 `sg pr view` 回读完整标题，再通过 `sg pr edit` 最小替换标题开头第一个 `#YYYYMMDD#`；不要为了指定日期手写整段标题前缀
- 标题括号只基于当前阶段全部绑定仓库中“实际有 diff 的配套改动集合”判断，包含本任务已有 PR 或本次未选中创建 PR 的配套仓库；不把无 diff 的仓库或历史阶段仓库算进去。即使用户只要求“后端创建 PR”，仍要核对本任务其它端的配套改动
- 标题里的任务名优先取 `current_stage.task_name`，其次取 `current_task_name`，最后取 `task_id` 去掉日期后的名称
- 每个 PR 先排除当前仓库，再把其它配套仓库的具体端标签去重，按 `PC端、手机端、后端、平板端` 顺序写入 `（有...）`；其它端标签排在后面。同一端有多个配套仓库时只写一次；如果另一个仓库与当前仓库同属手机端等同一类型，它仍是配套仓库，不能仅因端类型相同而省略
- 端标签优先读取 `repositories.yaml` 仓库项的可选 `pr_platform`，例如 `PC端`、`手机端`、`后端`、`平板端`、`小程序端`。未配置时沿用仓库 key / notes / aliases 和现有 runtime 分类识别常见端；平板 / tablet / iPad 标记优先于手机端识别，不再把 PC、手机和平板笼统合称“前端”。PR 端标签不改变发布命令分类
- 本任务同时有 PC、手机、后端、平板四个仓库改动时，后端 PR 为 `采购优化（有PC端、手机端、平板端）`，手机端 PR 为 `采购优化（有PC端、后端、平板端）`；只有当前仓库有改动时省略括号
- 无法判断配套仓库的实际 diff 或端标签时，先报告具体缺失项；端标签可补充 `pr_platform` 或向用户确认，不猜测、不静默遗漏
- 脚本或 AI 拼默认标题时，复用 `scripts/task_workflow_lib.py` 的 `build_pr_default_title(...)`；参数 `changed_pr_repo_keys` 传入本任务全部实际有 diff 的仓库集合，不仅是本次选中创建 PR 的仓库集合
- 用户显式提供 `--title` 时，完全使用用户标题，不再自动拼默认标题
- 在目标仓库根目录创建：默认使用解析后的新版 `sg` 绝对路径执行 `sg pr create --target <远程默认分支> --wip`；按用户提供或默认生成的 `--title`，以及用户提供的 `--desc`、重复的 `--reviewer` 与 `--task-link` 追加参数
- 如果用户只用自然语言说 `bbsid: 52040` 这类编号，按既有上下文能确定完整 BBS 链接时再转成 `--task-link <BBS链接>`；不要把纯编号直接传给 `--task-link`
- 对已有开放 PR 做日期更新时，先用 `sg pr view` 读取完整标题，再通过 `sg pr edit` 只替换标题开头第一个 `#YYYYMMDD#`；不得替换后续 `#BBS#`，不能用短标题覆盖完整标题。编辑后再次 `sg pr view` 回读确认，确保 `WIP:`、BBS 编号、任务名和配套端后缀都保留
- 用户传 `--no-wip`，或明确说“取消 WIP / 不要 WIP / 创建正式 PR”时，调用 `sg pr create` 时省略 `--wip`；不要把 `--no-wip` 透传给 `sg pr create`，它只是 task-workflow 层的意图参数
- `--reviewer` 可重复；取消 WIP 只影响是否追加 `--wip`，不改变目标分支、标题、描述、reviewer 或授权边界
- `sg pr create` 失败时只展示命令输出和错误，不改用 `glab` / `gitlab` 等客户端，不自动重试或修改既有 PR
- 创建、找到已有 PR 或编辑标题后，将已回读核对的结果登记到当前阶段的 `pull_requests`，按下节合并更新；本地登记失败时报告“远程操作成功、记录未完成”，后续接续原 PR，不重复创建。

示例：

```bash
sg pr create --target master --title "采购优化（有PC端、手机端、平板端）" --reviewer alice --wip
```

### PR 记录与复用

- 每阶段在 `meta.yaml` 的 `current_stage.pull_requests` 保存列表；历史阶段放在所属的 `previous_phases[].pull_requests`。每条字段为 `repo_key`、`source_branch`、`number`、`title`、`url`、`verified_at`（带时区的实际核对时间），分别来自绑定仓库、已核对的源分支与 PR 返回结果。标题保存完整内容，不自行拼 URL 或丢掉日期、BBS、配套端。
- 以实际仓库身份与 PR 编号标识 PR；同编号在不同仓库是不同 PR。相同 PR 重复登记合并更新，不追加重复记录。标题变更时可在 `previous_titles` 保留曾核实的完整旧标题，便于识别改日期前的审查消息；旧标题不能覆盖当前标题。记录不包含仓库审查人分工。
- 普通 Load、`fix` 消息匹配及 `reply` 拼链接优先读取缓存，核对记录仍属于当前阶段、绑定仓库的本地 origin 身份和源分支即可复用；不为展示标题和链接每次全量 `sg pr status/view`。缓存只是身份与标题快照，不证明 PR 当前仍开放、已批准、可合并或代码已推送。
- 缓存缺失、源分支或仓库不符、同标题对应多个 PR、消息链接与缓存冲突、疑似改名或重新建 PR，以及本轮需要判断远程当前状态时，才定向查询受影响仓库和 PR。实际创建/编辑 PR 的防重复和回读规则仍执行，不因有缓存而省略。
- 无缓存时先检查该阶段已有 progress / 原始 PR 回执，存在可核对的仓库、分支与真实 PR 信息就补录，保留原核对时间；缺少核实依据时，在对应仓库根目录用 `sg pr list --head '<记录分支>' --state all --json localId,title,webUrl` 找候选，再用 `sg pr view <编号>` 核对详情与源分支。候选不唯一、查询截断或身份不符时停止认领，不选标题最相似的一项。字段及 CLI 能力以当前 `--help` 和实际输出为准。
- 只记录查询实际取得的事实；查询失败不清空已有记录，不填假的核对时间或状态。创建/回读失败不登记为成功。老任务缺少 `current_stage` 时，按现有顶层阶段事实补建当前阶段壳，保留状态、许可、分支、方案和 BBS，不借登记改变开发准入。
- `next` 将当前记录随原阶段归档，新阶段不继承；`stage` 恢复目标阶段自己的记录，不跨阶段混用。手工修改记录分支后，旧源分支的 PR 记录不能继续当作当前 PR。

## Save / Push

用于只把当前任务仓库代码保存到远程任务分支。

以下规则针对用户独立要求 save-only。自动开发闭环的验证、hook 修复和有限重试按 [auto-mode.md](auto-mode.md) 处理，成功后仍逐仓核验远程结果；本轮明确只保存时不得顺势继续开发。

自然语言触发：
- `提交到远程`
- `推送一下`
- `保存代码`
- `先把代码推上去`
- `代码先提交`

规则：
- 默认不指定目标时，处理当前任务下有本次改动的绑定仓库；指定目标时，继续使用和 publish / sync 一样的自然语言目标识别方式
- 执行前先加载当前任务的 `meta.yaml`，确认目标仓库存在，当前分支与记录分支一致
- 先检查 `git status --short` 和本次相关 diff，暂存前排除无关 dirty 文件、其它任务文档和其它仓库改动
- 按仓库独立 commit / push；无改动仓库不创建空提交
- 首次推送任务分支时允许 `git push -u origin <当前分支>`；已有 upstream 时普通 `git push`
- 推送后用 `git status --short --branch`、upstream ahead / behind 或远程 SHA 确认保存成功
- 不运行测试、类型检查、lint、构建、真实页面验收或发布命令
- 不运行 `prepare_task_runtime.py`，不安装依赖，不修复 `node_modules`，不处理前端 native binding 缺失
- commit hook 失败时展示 hook 输出并停止该仓库；hook 修改文件时展示新增改动，不自动继续提交
- 默认不使用 `--no-verify`，除非用户明确授权跳过 hook
- save-only 不更新任务状态；如果需要记录进展，只能在 `progress.md` 中简短记录“已推送保存”，不要写成已验证或已完成

## Publish

显式命令：

```text
/task-workflow publish [目标1] [目标2] [目标3...]
```

规则：
- 用户显式输入 `/task-workflow publish ...` 时，视为已授权直接执行发布动作
- 默认不指定目标时，发布当前任务下全部绑定仓库
- 一次可以传多个目标
- 一次多个目标时，先统一识别并校验目标，再并行发布
- 发布前先校验任务绑定仓库是否存在，以及当前分支是否与 `meta.yaml` 记录分支一致
- 普通发布正式执行前，必须先按完全相同的目标集合调用现有 `clean-develop` 指令 / `clean_develop_task_workspace.py`；本地 `develop` 已删除或本来不存在（no-op）后，才允许执行 `sg publish`
- `clean-develop` 出现普通失败时，该目标不得继续发布；多目标的其它目标按独立失败规则处理。若目标已经停在 `develop` 的合并冲突或冲突解决重试现场，不删除当前分支，按下方 `develop` 冲突规则保留现场并继续重试
- 如果上一次发布已把仓库停在 `develop` 冲突处理或冲突解决后的重试状态，允许从 `develop` 继续发布，不要强制切回任务分支
- 配置为 `patch-node-frontend-environment` 的前端仓库，执行 `sg publish local` 前只自动执行当前平台原生 optional 依赖准备；这是本地发布环境准备，不是业务代码改动
- 发布前不要调用完整 runtime prepare；不要在 publish preflight 中生成端口、改写前端代理或重写 `environment.toml`
- 如果原生 optional 依赖准备报错、修复后仍缺当前平台原生 optional 依赖，或导致 `package.json` / `package-lock.json` 产生新 diff，停止发布该仓库并展示 prepare 错误，不继续执行 `sg publish local`
- 前端发布不能只看 `sg publish local` 的退出码；终端输出含 `发布成功`、单独一行 `success`、`status: success` 或 JSON `{"status":"success"}` 时视为成功；终端成功提示被非交互环境静默时，退出码为 0 且按命令、子命令、仓库路径和本次执行时间精确匹配的 CLI 日志记录为 `status: success`，也视为 CLI 发布成功
- 退出码为 0，但既没有明确终端成功信号，也没有本次精确匹配的 CLI 成功日志时，结果为 `UNCERTAIN`；只展示缺失的证据，不自动重复发布
- 后端发布也应优先看终端中的明确成功信号；如果没有明确成功信号，或 CLI 日志记录为失败，就不能汇报为 `OK`
- 某个目标发布失败时，不应阻断其它目标；应继续完成其它目标，并明确展示失败仓库的错误信息
- 普通发布失败后，默认停在“展示失败信息”这一步，不自动进入修代码、补提交或重试发布
- 如果失败原因是工作区不干净、分支异常或发布命令本身报错，默认只反馈事实，不自行修复，除非用户明确要求继续处理

固定命令：
- 发布前置：`python3 /Users/wuyongli/Documents/sg-skill/task-workflow/scripts/clean_develop_task_workspace.py "<task-id>" [目标...]`
- 后端仓库：`sg publish jenkins`
- 前端仓库：`sg publish local`

### `develop` 冲突

- `sg publish` 在合入 `develop` 发布阶段留下本地合并冲突时，不按普通发布失败处理
- `develop` 发布冲突必须保留冲突现场：不要 `merge --abort`，不要切回任务分支，不要尝试在任务分支解决这个冲突
- `develop` 发布冲突优先由 AI 在当前 `develop` 工作区自动解决；只有冲突语义、业务口径或保留策略不明确时，才停下来问用户
- 解决 `develop` 冲突后，先运行与冲突文件相关的最小验证；验证通过后，从当前 `develop` 状态重新发布
- 从 `develop` 重试发布成功后，必须切回 `meta.yaml` 记录的任务分支，避免后续开发误改 `develop`
- 如果发布成功但切回任务分支失败，应明确报错并停止，不要把任务汇报为完全完成

### 发布后的 Bug 交测

- 发布后只核对当前任务、当前阶段中已通过 `bug` 处理并记录待发布的项。普通 `publish` 接续这些 Bug 已获授权的状态回写，本轮“只发布”等更窄限制优先。没有待交测记录时结束此步骤，普通优化随批次发布即可。
- 逐项对照 `progress.md` 中 Bug 所需的仓库和修复提交，核对测试服发布结果及实际版本。只有本次成功发布包含该 Bug 的修复，并且其余依赖的修复也已确认在测试服生效，才执行[待验证流转](bugs.md#回写处理结果与状态)。已在先前批次发布的仓库可复用仍有效的测试服版本证据。一个仓库失败只阻断依赖该仓库的 Bug。
- 发布成功需要对应到实际部署的代码。核对部署版本包含修复且改动未被回退或覆盖。无法直接核对版本时，按 [verification.md](verification.md) 取能确认该项修复已生效的测试服证据。发布失败、结果 `UNCERTAIN`、尚有仓库未发布或无法确认完整修复已生效时，继续保留待发布记录，写明缺项。
- 在 `progress.md` 分别记录各仓库的发布证据和各 Bug 的 Test Hub 回读状态。发布已成功但流转失败时保留发布结果，下次通过 `bug` 接续，只补核对和状态流转。后续无关发布按各自批次处理。
- 汇总本批已回读确认待验证的 Bug，按测试人员合并钉钉单聊，并记录通知结果。收件人核对、发送和补发按 [Bug 交测通知](bugs.md#钉钉通知测试人员) 执行。

## Sync

显式命令：

```text
/task-workflow sync [目标1] [目标2] [...]
```

规则：
- 默认不指定目标时，同步当前任务下全部绑定仓库
- 指定目标时，继续使用和 publish 一样的自然语言目标识别方式
- 多仓库同步默认并行执行，不强调顺序
- 每个仓库同步前先检查当前分支是否与 `meta.yaml` 记录分支一致
- 如果某个仓库有未提交的本地改动，不继续同步该仓库，应直接展示该仓库的 `git status --short` 结果
- 同步过程默认先 `fetch origin --prune`，再把远程默认分支合入当前任务分支
- `fetch` 本身不使验证失效；实际合入新提交、执行 rebase 或解决冲突后，原验证对受影响范围失效，后续 Review / PR / 发布只补跑相关验证
- 如果同步过程中出现冲突、工作区异常、分支异常或 git 命令报错，只反馈事实和错误信息，不自动修代码、不自动解冲突、不自动继续处理
- 某个仓库同步失败时，不阻断其它仓库；其它仓库继续执行，最后统一汇总成功和失败

推荐命令：

```bash
python3 /Users/wuyongli/Documents/sg-skill/task-workflow/scripts/sync_task_workspace.py "YYYY-MM-DD-原始任务名"
python3 /Users/wuyongli/Documents/sg-skill/task-workflow/scripts/sync_task_workspace.py "YYYY-MM-DD-原始任务名" 后端 手机前端
```

## Clean Develop

用于发布前删除任务仓库里的本地 `develop` 分支，避免后续 `sg publish` 合入远程 `develop` 前受到落后的本地 `develop` 影响。

显式命令：

```text
/task-workflow clean-develop [目标1] [目标2] [...]
```

规则：
- 只删除本地 `develop` 分支，不删除、不推送、不改动远程 `origin/develop`
- 默认不指定目标时，处理当前任务下全部绑定仓库
- 指定目标时，继续使用和 publish / sync 一样的自然语言目标识别方式
- 多仓库默认并行执行，不强调顺序
- 某个仓库没有本地 `develop` 分支时，视为 no-op，不影响其它仓库
- 如果某个仓库当前分支就是 `develop`，不删除该仓库的本地 `develop`；先输出当前分支状态，等待用户或 AI 切走后再重试
- 删除失败时，只展示失败仓库和 git 错误信息，不自动切分支、不自动修复工作区

推荐命令：

```bash
python3 /Users/wuyongli/Documents/sg-skill/task-workflow/scripts/clean_develop_task_workspace.py "YYYY-MM-DD-原始任务名"
python3 /Users/wuyongli/Documents/sg-skill/task-workflow/scripts/clean_develop_task_workspace.py "YYYY-MM-DD-原始任务名" 后端 手机前端
```
