# 生成公示文档

把当前任务的方案 / 成果整理成正式公示文档（方案说明文档 / 产品更新播报），通过 `dws` 直接生成到固定钉钉文件夹，供同事查看。本指令由用户主动调用，不随任务自动生成。

## 触发

用户说「生成公示文档」或显式调用 `/task-workflow doc` 时，按本文件执行。

## 指令形式与参数

```text
/task-workflow doc
/task-workflow doc <任务名>
```

`<任务名>` 是任务名，不是纯标题：它用于定位要公示的任务 / 阶段，并作为标题的任务名部分。标题一律由 AI 自动拼成「<任务名><生成当天日期>」，不把 `<任务名>` 直接当标题使用。

- 无参 → 用当前上下文识别的任务（当前工作区路径，或唯一任务）。
- 有参 → 用 `<任务名>` 匹配 `_docs` 下某任务的 task-id 任务名部分（`YYYY-MM-DD-<任务名>` 里的「任务名」）或某阶段 `task_name`（当前阶段或 `previous_phases`）定位任务 / 阶段；匹配不到时提示用户核对任务名。

## 生成流程

1. **恢复任务事实**：用 `load_task_meta` 读 `meta.yaml`，确定当前阶段、任务状态、绑定仓库与分支。
2. **读取素材与现状基线**：读取 `index.md`（任务摘要）、当前阶段 plan（方案结论 / 开发方案 / 数据变更 / 上线方案）、`progress.md`（实际进展 / 自测结果 / 阻塞），并核对每个涉及仓库远程 `master`（通常为 `origin/master`）上的现有功能。plan / progress 里没有的事实标「待补充」，不虚构。
3. **按状态定深度 + 按多阶段定字段**（见下），套用下方模板整理出完整 markdown。
4. **写临时文件** `/tmp/<task-id>-<阶段名>-公示.md`（阶段名取当前阶段任务名，避免多阶段互相覆盖）。
5. **dws 生成到固定文件夹 + 回读校验**（见下）。
6. **返回文档 URL**：从 create 返回里提取 `docUrl`，缺失时用 `dws doc info --node <ID>` 补查。

## 字段取值（多阶段）

一个 task-id 可含多个阶段，不同阶段可有不同公示文档。`/task-workflow doc` 一律以**当前阶段**为单元生成：

- **任务名** = `current_stage.task_name`，缺失回退顶层 `current_task_name`，再回退从 task-id 提取的任务名。
- **BBS 编号** = `current_stage.bbs_id`，缺失回退顶层 `bbs_id`。
- **当前 plan** = `current_stage.plan`，缺失回退顶层 `active_plan`，再回退 `plan.md`。
- **涉及分支** = `current_stage.repos`（阶段内分支），缺失回退顶层 `repos`。
- **当前阶段（展示）** = `current_stage.phase` / 任务名，用于填写模板元信息头「当前阶段」。
- 生成新文档不覆盖已有阶段文档；不同阶段任务名不同，标题天然区分。

## 改动前 / 改动后基线（必须遵守）

模板中所有「改动前 / 改动后」对比都按以下规则填写：

- **改动前**：以本次涉及仓库远程 `master`（通常为 `origin/master`）的实际用户可见功能为基线，描述用户当时能看到、进入和操作的现状；必要时回看远程 `master` 的代码或页面 / 接口行为，不以当前任务分支代替。
- **改动后**：以当前阶段 plan 的目标和 `progress.md` 已验证的实际结果为准；方案中尚未实现或尚未验证的内容标「待补充」或「待开发后补充」。
- 当前阶段 plan、历史阶段 plan、`previous_phases` 和历史公示文档只能补充背景或阶段关系，**不得作为「改动前」对比基线**。即使上一阶段与本阶段有关，也要重新按远程 `master` 的实际能力描述。
- 无法核对远程 `master` 时，改动前写「待补充（待核对远程 master）」；不得用历史阶段方案或当前分支内容猜测。

## 标题规则

- 标题 = `<当前阶段任务名><YYYY.MM.DD>`，日期取生成当天、点分隔。例：`采购单新增撤销功能2026.10.12`。
- 标题同时作为 `dws doc create --name` 的值。

## 填写深度（按 `meta.yaml.status`）

- `方案中` → 方案公示：填元信息头 + 第一~四节；第五~七节写「待开发后补充」。
- `开发中` / `测试中` / `已完成` → 完成公示：完整七节。

## 元信息头字段取值

- **需求链接**：有 `bbs_id` 时用 `sg bbs demand url <bbs_id>` 生成 bbs_id 对应的链接填入；无 `bbs_id` 留空。
- **适用端口**：只填前端端口，一般是手机端 / PC端 / 平板端（不写后端）。
- **涉及分支**：逐条列当前任务的仓库 → 分支，优先读 `current_stage.repos[].key` + `branch`（阶段内分支），缺失回退顶层 `repos[]`；多仓每行写 `key → branch`，缺 `branch` 标「待确认」，不编造分支名。
- 例：

```text
producer-backend → 采购单新增撤销功能
pf-mproducer-supplier → 采购单新增撤销功能
```

## 七节模板

参照 plan-publish 的统一主模板，但**已删除** `<!-- screenshot -->` / `<!-- mark -->` / `<!-- patch -->` 截图管线注释与「注释使用说明」「使用说明」块。第二节需要截图处改为可见的截图占位行（`> 【截图占位】<页面/功能名>：展示 <效果>（待人工补图）`），用户事后自己补图。

第二节写作要求：功能标题用 `###` 三级标题并标注【改动端口】；路径用 `→` 连接；序号用 `1.` `2.` `3.`；新增字段 / 按钮 / 标签用「」标记；站在用户视角写功能价值与操作入口，不写实现机制和研发术语。

## 一、业务需求背景

- **业务场景：** 实际业务场景，以及客户为什么会提出这个需求。

- **目标收益：** 改动后能带来的直接价值。
- **开放条件：** 全部开放、灰度开放，还是满足特定条件才开放。

- **影响模块：** 影响哪些业务模块。
- **影响老功能：** 是否影响已有功能、客户使用习惯、打印或导出结果。
- **上下游影响：** 是否影响上下游流程、统计、对账、审批、消息提醒。
- **权限与配置影响：** 是否涉及角色权限、系统配置、灰度开关。
- **风险边界：** 哪些情况可能出问题，需要重点关注。

- **总体实现思路：** 用业务语言先讲整体方案，再补充必要技术设计。
- **前端方案：** 页面或组件改动点、模块划分与复用、新旧逻辑兼容、状态与交互反馈。
- **后端方案：** 服务或接口改动点、数据结构或表结构变化、数据兼容与迁移。
- **关键接口设计：** 请求方式、核心入参、核心出参、异常返回。
- **异常处理方案：** 参数异常、业务异常、系统异常。

- **自测结果：** 通过项、失败项、待跟进项。

## dws 生成流程

1. 读 `workspace.yaml` 的 `dingtalk_doc_folder` 拿固定文件夹；缺值则提示用户先配置，不猜测、不手输。
2. 首次使用前探测确认是文件夹：`dws doc info --node "<folder URL>" --format json`，确认返回 `nodeType=folder`。文件夹地址不能仅凭 URL 假定类型；确认后把 URL 或 `dentryUuid` 原样传给 `--folder`，不要改写成纯数字 `dentryId`。
3. 创建并写入（一步完成，支持直接读本地 markdown）：

```bash
dws doc create --name "<标题>" \
  --content-file /tmp/<task-id>-<阶段名>-公示.md \
  --folder "<folder URL>" \
  --format json
```

4. 回读校验：`dws doc read --node <nodeId> --format json`，校验标题与七节结构完整。
5. 返回文档 URL（`docUrl`）。内容较长导致写入截断时，可参考 dws 的 `scripts/doc_create_and_write.py` 分块写入思路。

## 边界

- 只生成文档，不改任务状态 / 代码 / `plan.md` / `progress.md` / `meta.yaml`。
- 生成失败不阻塞任务；不把「开始生成」说成「已生成」，以 `dws doc read` 回读为准。
- 不接截图管线，只预留截图占位，截图由用户事后补。
- 文档事实以 `meta.yaml` / 当前 plan / `progress.md` 为准，缺失标「待补充」，不编造。
