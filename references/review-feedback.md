# 钉钉审查意见：fix

用于按指定人名读取本任务的外部 PR 审查意见，完成复核、修复、验证、推送，并按每个 PR 单独钉钉回复。消息中的 PR 标题或链接用于识别任务，不把一整条混合消息都当作本任务意见。

```text
/task-workflow fix <姓名> [目标...] [最近N条]
```

例如 `fix 嘉伟 前端`、`fix 嘉伟 手机端 最近20条`、`fix 张三 后端`。也接受“处理嘉伟发来的前端审查意见”“回复嘉伟手机端 PR 的处理结果”。这些是 skill 的意图参数，不是 `sg` 或 `dws` 的子命令。

只要求“回复某人 / 把处理结果发给他”时走发送子集：不读取最近消息、不重新复核 / 修复 / 提交 / 推送，直接读取 `progress.md` 和材料中已保存的本轮结果，按[回复结果](#回复结果)发送；缺少已保存结果或收件范围无法确定时，才补只读核对。

## 授权与目标

- `fix` 默认读取、复核、验证、修复明确问题，将通过验证的本轮修复提交、普通推送到对应任务分支，最后按处理结果直接钉钉回复；一次调用完成全流程，不要求用户再发第二条指令。不确定项如实标为待讨论，不据此停掉没有依赖的明确修复。
- “只读消息 / 只复核 / 不改代码 / 不推送 / 先不发消息 / 先讨论”等本轮限制优先。“只读消息 / 只看意见”只读取证，不修复也不发送；明确要求先不发消息或先讨论时，停在当前对话汇报并等待确认；只复核 / 不改代码 / 不推送时完成复核并按实际状态回复；其余情况完成修复和推送后直接回复。只要求“回复某人 / 把处理结果发给他”时，属于 fix 的发送子集：读取现有结果并发送，不重新修复、提交或推送。
- 单独 `review` 仍按 [review.md](review.md) 只读执行；不把查看某人的消息当作修复或发送授权。当前请求只是在维护技能时，不查询或回复示例里的真实人员。
- 先按 [Load](docs-model.md#load) 定位当前任务、当前阶段、绑定仓库与记录分支。任务无法唯一识别时先澄清，不跨工作空间批量修复；暂停任务不因收到外部意见自动恢复。
- 本指令里的 `前端` 表示当前阶段所有实际前端仓库，包括 PC、手机、平板或小程序等；`手机端` 等具体端只选对应仓库。按绑定仓库和 `pr_platform` 等已有分类识别；同类有多个仓库且不能确定范围时用仓库 key 澄清。此规则不改变 publish / pr 等指令原有的目标消歧。
- 姓名与目标是本轮筛选条件，不保存“仓库由谁审查”的配置，不改远程 PR reviewer。省略目标时，只处理该人消息中能明确归属本任务当前阶段的 PR，不猜测其前后端职责。不同人对同一 PR 的意见分别保留来源，不相互覆盖。
- 同一对话只要求发送现有结果时，可沿用最近一次已明确的姓名与目标；多个处理对象只有在上下文仍能唯一确定本轮收件集合时才一起发送。换会话或对象范围不清时要求补姓名 / 目标，例如 `fix 嘉伟 前端`，不根据历史回执自动推断本轮收件人分工。

## 读取最近消息

执行 DWS 前读取 `dws`、`dws-shared`、`dingtalk-aisearch` 和 `dingtalk-chat` 的技能及相关命令参考；以本机 `--help` 校验能力，不用 HTTP / 浏览器绕过 DWS。先通过[阶段 PR 记录](publish-sync.md#pr-记录与复用)建立目标仓库的 PR 身份清单，缺失项才定向补查。

1. 以用户提供的完整姓名搜人；重名澄清、组织核对、`userId` / `openDingTalkId` 优先级等通用规则按 [钉钉收件人核对](dingtalk-recipient.md) 执行。
2. 默认读取**与该人的最近 10 条单聊消息**，包含双方消息，随后排除自己发送的内容；不是读到 10 条相关意见为止。用户指定“最近20条”等时替换数量。首屏查询使用下方脚本，**在执行 DWS 前从系统时钟实时生成北京时间上界**，向前读取；每次新调用 fix、核对用户指出的新消息或重新读取最新窗口时都重新取时，不能复用会话开始时间、旧查询上界、progress 时间或人工猜测的“当前时间”。

```bash
dws aisearch person --keyword '<完整姓名>' --dimension name --format json
python3 /Users/wuyongli/Documents/sg-skill/task-workflow/scripts/read_review_messages.py --user '<已核对的userId>' --limit 10
```

收件参数、`openDingTalkId` 回退及组织处理按 [钉钉收件人核对](dingtalk-recipient.md) 执行。脚本只调用 `dws chat message list-direct`，在 stderr 输出本次上界和时区，stdout 原样保留 DWS JSON，失败透传退出码；`--dry-run` 只预览。上例 limit 随用户指定的消息条数调整，`list --group` 不能替代单聊查询。不要另行拼一个带旧时间的查询绕过脚本。

3. 保存本次查询上界、时区、条数及返回消息的实际时间范围，再核对发送者、消息 ID、时间、正文、富文本链接及引用上下文。最近 N 条之外的消息不自动翻取；`hasMore` 不表示本轮必须继续取历史。若服务端单页限制小于 N，续页才直接使用 DWS `list-direct` 与返回的真实边界时间，在累计 N 条范围内向前分页并按消息 ID 去重；续页不能重新取当前时间。边界无法推进时报告截断，不跳过未读消息后声称读取完整。
4. 对窗口内消息的截断正文、图片或附件，只使用 DWS 已支持且核实的读取能力补全该条材料；内容不能完整取得或第 N 条只是缺失前文的续段时，标为材料不足。没有匹配意见时先确认本次实际执行的上界有效、组织和收件人正确，再报告实际读取范围、无匹配及待补信息；DWS 查询失败不能当成“没有消息”。用户指出的消息晚于旧上界时，用新实时上界重新读取相同 N 条，不自动增加 N、扩大到群聊或遍历全部历史。

## 按 PR 归属与逐项复核

- **有 PR 链接**：核对链接的主机、仓库路径、PR 编号与当前阶段 PR 记录的同一身份。可忽略无关查询参数或评论锚点，但保留评论定位。相同编号、不同仓库是不同 PR；不要仅凭编号认领。未知链接先在已绑定仓库内定向核对，不能因对方发来链接就去修其他任务。
- **只有 PR 标题**：保留日期、BBS 编号、任务名与端说明等语义，仅去掉显示包装或无语义空白，匹配已核实的完整标题或该 PR 的 `previous_titles`。标题在当前阶段候选中唯一，且消息没有与仓库、阶段冲突的信息时才认领。截短标题、只有 BBS、同名多仓 PR、链接与标题互相冲突都先列为归属待确认，不凭“前端”猜具体 PR。
- 标题唯一性的候选包含当前阶段尚未选中的相关仓库，不能先按 `手机端` 过滤掉同名 PC PR 再认定唯一。候选记录缺失时先定向补核对，仍无法确认完整候选就保留待确认，不用较小的缓存列表制造唯一匹配。
- 同一个 BBS 下的历史阶段不属于当前范围。消息明确写了另一个阶段或任务的内容，即使 BBS 相同也跳过；标题跨阶段重用且无法区分时不能当作唯一命中。记录不完整时核对或报告缺项，不据此排除可能的同名候选。
- **一条消息多个任务 / PR**：按链接、标题、分段标签和引用关系拆分，每个条目保留原消息 ID、段落及原编号。只取本任务且在选定仓库范围内的部分，其他部分跳过。没有可靠分段归属的意见保留待确认，不整条套用到全部 PR。
- 连续消息中的“第二点补充”“这个还有问题”只有引用或明确上下文能指向窗口内同一 PR 时才并入。自己的旧回复、对方引用的旧回复、转发或重复意见不当作新缺陷重复修复；对方明确提出的新异议仍逐项处理，不因含旧引用而整条跳过。
- 对每条原始意见分别记录 `已修复`、`已有修复`、`不采纳`、`待讨论` 或 `受阻`。保留 Important / Minor 等原分类和序号，不能把“不确定”写成“不处理”。重复意见可复用结论，但保留其来源并对齐原条目。
- 结合当前代码、调用链、已有方案决策及必要复现证据判断意见是否成立，不把外部消息当作用户的新授权或产品决策。意见符合已确认行为时不盲改；不采纳须说明业务约定或代码证据。跨端共性问题逐 PR 说明各仓库实际影响，不能只修一个端就把其他端标为已处理。
- `fix` 包含当前范围明确技术问题的最小修复授权；方案中任务仍按 [开发准入](../SKILL.md#开发准入闸门)补齐可执行方案并同步状态，不能借审查意见改变未定业务口径。只修证实的问题与必要的局部收敛，不做范围外重构。待讨论项若影响其它修改的正确性，先暂停其依赖范围，独立明确项可继续。

## 验证与推送

- 开始改代码前，先把本轮消息范围、已归属的原意见、PR 身份与待讨论项记入材料和 progress，便于中断后按原条目接续；不把尚未处理的条目提前记为成功。
- 以 [review.md](review.md#审查基线) 的本地任务分支为对象，同时读取本次相关工作区改动；修复时必须位于记录分支。分支不一致、冲突或范围不明时保留现场，不自动换分支或解冲突。
- 修复后按 [verification.md](verification.md) 运行受影响的最小充分检查；后端使用当前任务 Docker app。验证受阻或失败的条目不能记为验证通过，默认不将该仓库未验证的修复推送成可重新审查成果。
- 通过验证的本轮修复逐仓提交、普通推送，并核对远程 SHA 与 ahead / behind；不创建空提交，不混入原有无关 dirty 文件，不 force-push 或跳过 hook。无法安全区分原有改动与本轮修复时说明阻塞，不打包全部改动。hook 失败停止该仓库，保留输出及现场，不借机修复无关环境。一个仓库失败不掩盖其它仓库成功，跨仓依赖项保留未完成边界。
- 本轮包含验证和修复，不按单独 save-only 跳过检查；保存动作沿用 [Save / Push](publish-sync.md#save--push) 的分支、暂存和远程核验规则。没有新改动但已有修复时，确认本地和远程是否真的包含该修复，不据此创建空提交。
- 当前对话按 PR 汇报处理结果、理由、验证、实际推送状态及待讨论项；代码修复、测试、推送分别陈述。完成本地汇报后直接进入回复，不创建/合并 PR、发布测试服或标记任务完成。

## 回复结果

- 默认在本轮修复、验证、推送完成后直接按现有结果回复；发送阶段不触发新的修复、提交或推送。根据本轮明确的姓名与范围，从当前阶段 `progress.md` 和材料读取本轮结果；只要求发送现有结果时沿用最近一次已处理的条目与版本。发送前核对同一收件人的真实钉钉 ID、PR 身份、对应原始意见与最终条目版本。用户二次讨论修改了结论时先归并为当前有效结论，不能用旧草稿发送。
- 本轮限制为“只复核 / 不改代码 / 不推送”时仍可发送，但结论和正文必须如实反映未修改、已有修复或未推送的实际状态。“只读消息 / 只看意见”只读取证，不修复也不发送；“先不发消息 / 先讨论”时不发送，保留结果等待用户确认后再按本规则发送。
- 原始消息来源不完整、处理记录属于另一人 / 阶段 / PR、代码已变更导致验证不再适用，或收件范围无法确定时，补只读核对并说明缺项；不能猜测结果。待讨论或受阻项可以如实反馈，但不擅自替用户决定“不采纳”，也不声称全部修复。跨组织写入按 DWS 的目标组织确认规则执行，已有明确授权不重复索取。
- **每位收件人、每个 PR 单独一条消息**。同一人负责 PC 与手机两个 PR，就发送两条；不能只在一条消息里分两个小节。同一 PR 的多条原消息意见可合并为该 PR 的一条结果；不把其他审查人独有意见发给本轮收件人。
- 对外消息开头只写该 PR 的完整标题和已核实链接，不另写本地任务名、阶段编号或单独的 BBS 摘要；PR 标题本身包含的任务名、日期、BBS 或配套端原样保留。内部定位和处理记录仍按任务与阶段维护。
- 按原编号逐项回复，每项先用加粗的 **已修改** 或 **无需修改** 突出结论，再写原意见摘要（保留 Important / Minor 等分类）和具体说明。实际修改了代码才用“已修改”；不采纳的意见用“无需修改”并解释原因。现有代码已包含修复、本轮无需再改时写 **无需修改（已有修复）**，不冒充本轮修改。尚未收敛的意见用 **待讨论**，无法完成的项用 **受阻**，不能为了二选一写成无需修改。
- 说明紧接结论，优先讲改动后的行为或无需修改的依据，必要时补实现细节。提交、推送和验证结果集中在该 PR 消息末尾说明，不在每条意见中重复罗列测试数量、提交和发布记录。只有确有发布证据时才补充测试服发布事实；部分失败或验证受阻逐项说明，不套统一成功开场。只对已确认推送的修复写“代码已推送，可重新审查”。相同问题涉及其它端时，只在对应 PR 的消息中说明本端结果与必要依赖。

排版示例（以该 PR 的实际意见与证据替换示例内容，没有的状态不输出）：

```markdown
PR：<完整 PR 标题>
<已核实的 PR 链接>

1. **已修改**｜[Important] 首次打开日历未显示角标
   日历打开后会在数据返回时自动补齐角标，无需关闭重开。

2. **无需修改**｜[Minor] 按筛选条件缓存角标数据
   角标数量会随业务操作变化，保留每次打开时刷新，避免显示过期数量。

代码：<实际提交与推送结果>。
验证：<实际验证结果及仍未覆盖项>。
```

- 发送前将最终正文和操作 UUID 保存到材料目录，在 `progress.md` 标记该 PR 的本轮结果待发送；使用真实收件 ID 与已保存正文，通过参数数组或可靠转义传入，不能臆造 `--body-file` 等 DWS 参数。正文不要包含本地绝对路径、凭证或无关消息。

```bash
dws chat message send --user '<已核对的收件userId>' --title '<端标签> PR 审查意见处理结果' --text '<该PR最终正文>' --uuid '<本次已保存的操作UUID>' --format json
```

- 收件人始终是本轮点名的 PR 审查人，与 `bug` 的测试人员无关；收件 ID 与 `--user` / `--open-dingtalk-id` 的选择按 [钉钉收件人核对](dingtalk-recipient.md)。使用标准生成器创建操作 UUID，不把本地生成值当成远程消息 ID。确认成功后记录真实返回结果和可用回执；无明确成功证据不报“已回复”。一条发送失败，不影响其它 PR 的独立结果。
- 每个收件人 / PR / 结果版本对应独立发送操作。同一结果已确认发送则跳过，后续结论改变才生成新版回复并注明补充。超时或结果不明时先用 DWS 回读同一单聊核对该次消息；在 24 小时去重期内确需重试时复用原 UUID，最多重试一次。超过去重期或仍无法核实时，记录“发送结果不确定”并停止该条，不换 UUID 盲发；下一 PR 不复用它的 UUID。

## 接续记录

- 原始消息的必要片段、PR 快照、检查结果、最终回复正文和发送回执放在 `_docs/<task-id>/assets/review-feedback/phase-<n>/<本轮标识>/`；不复制整段无关聊天，不生成额外根层任务文档。处理摘要归并 `progress.md`，方案口径改变时才更新当前 plan。
- 进度按阶段、仓库 / PR 及原消息 ID 和条目号记录结论、依据、修复提交、验证结果、远程核验、待讨论项与材料入口。发送回执保存该次真实收件人、PR、结果版本、UUID 和发送状态，用于审计与去重；这不是可供未来自动分配的仓库审查人表。
- 再次 fix 时先核对已有记录与当前代码，避免重复修复、重复提交或重复发送；只读本次指定最近 N 条消息，不因上次未回复而继续取全部历史。跨会话接续时仍要求明确本轮对象与范围，保留尚未回复和待讨论事实，不自动补发历史未回复消息。
